# 纳川通用内核补全技术方案 V1

状态：K01–K06 已实施并通过本地通用内核验收（含干净包安装与回归）。日期：2026-10-31。实施结果与已知边界见 `内核V2验收记录_2026-10-31.md`。

## 1. 目标与完成边界

保留 Python 唯一宿主、TypeScript 业务插件、NDJSON JSON-RPC 子进程通信和本地文件持久化。沿用已修复的路由、租约、跨重载并发、流式归一化、热配置、巡检和基础任务设施。

本轮补齐四个通用闭环：插件声明契约、任意结构凭证、统一 Actions、多态额度。交付物包括宿主 API、插件 SDK/运行时、迁移逻辑及自动化验收。前端可在此后消费这些 API；真实平台适配也可在此后接入。

内核完成的门槛：两个不同凭证、动作、额度形态的测试插件，通过真实 Python → Node → 本地 HTTP 链路，完成加载、账号录入、调用、动作执行、额度同步、停用、轮换、重载与重启恢复。插件协议错误或崩溃必须被隔离。

本轮不包含：真实平台逆向、多租户、公网部署、计费级数据库、完整控制台开发，也不恢复旧 Cordis/Go 技术栈。旧规范中 Schema、隔离、公共服务等要求转化为当前 Python/TS 架构中的等价契约。

## 3. K01：冻结插件契约与协议协商

### 3.1 声明契约

在 spec.json 增加 specVersion: 2，保留现有 name/version/runtime/models/config，新增：

- credentialSchema：只描述账号秘密结构；required 字段按插件决定，不内置平台名称。
- settingsSchema：插件级配置校验，禁止与账号秘密混用。
- models[].capabilities 与 models[].optionsSchema：保留模型能力、专属参数约束；模型 ID 路由继续沿用现有规则。
- actions[]：动作 ID、显示名、输入/输出 schema、scope、timeoutSeconds、mutatesCredentials、idempotency、concurrencyKey。
- quota：支持的维度描述、是否提供 query、是否有可靠耗尽判断、快照有效期。
- tasks[]：引用已声明 actionId；继续支持 intervalSeconds。此阶段不新增 Cron 语言；若要求按时区的日历任务，作为额外验收项实现，不能宣称 interval 已满足 Cron。

配置 schema 和凭证 schema 必须分离。旧 configSchema 同时出现密钥和代理等字段，不自动推断全部为凭证字段；需提供显式迁移映射。现有四个骨架仍标记 legacy/experimental。

### 3.2 Schema 约束

冻结支持范围为对象、properties、required、additionalProperties、基础值类型、enum、字符串/数字边界、数组 items/长度；支持范围之外的关键字在插件加载时拒绝。以同一组合法/非法 JSON fixture 检查 Python 与 TypeScript 行为一致；不宣称完整支持所有 JSON Schema 特性。

模型额外参数只校验插件声明的字段；保留 OpenAI 标准字段。未知 vendor 字段遵循明确的 additionalProperties 策略，不静默丢弃。请求、日志和插件公开描述均不返回凭证值。

### 3.3 运行时协议

升级宿主为同时支持协议 1 和 2；协议 2 握手返回 models、实际实现的 actionIds、quota 查询支持、credential.validate 支持等。静态 spec 声明与实际实现不一致时，该能力标记 unsupported 或使声明为 required 的插件加载失败，不能显示可执行再返回假成功。

- 协议 1：保留现有 chat、health、refresh、task 调用，公开 capabilities 标记不足。
- 协议 2：新增 credential.validate、action.execute、quota.query；沿用 request.cancel。
- 缺少 handler 返回稳定的 unsupported 错误；不从动作名字猜业务实现。
- 插件 init 不需要真实凭证；没有账号也应能发现描述、添加第一个账号。是否允许聊天路由由账号就绪状态决定。

接口：GET /kernel/plugins/{name}/descriptor 返回经过校验的公开描述和实际能力；GET /kernel/models 返回含能力、参数 schema 的完整宿主模型目录。/v1/models 继续提供客户端兼容目录。

验收：坏 schema、重复动作、任务引用不存在动作、协议不兼容和虚假能力声明均有确定失败结果；旧协议插件仍可加载并完成已有调用。

## 4. K02：通用凭证仓库与账号管理

### 4.1 数据结构与秘密隔离

新增 CredentialStore，保存版本化 envelope：

```json
{
  "formatVersion": 2,
  "generation": 3,
  "account": { "enabled": true, "maxInFlight": 1 },
  "secret": { "cookie": "<private>", "csrf": "<private>" },
  "updatedAt": 1793440000
}
```

secret 完整视为秘密；即使 schema 未标注 password，也不进入公开快照。账号状态、额度快照、动作历史分别保存，不能把任意秘密字段平铺到状态文件。凭证文件 0600、目录 0700，临时文件同权限。

宿主负责结构校验；插件的可选 credential.validate 负责业务语义。上游探活与“凭证格式合法”分开返回，不把网络超时等同于凭证损坏。插件输出错误先转换为有界错误码/安全摘要，不直接把任意上游响应体写入事件历史。

### 4.2 API

- POST /kernel/plugins/{name}/accounts：{id, credential, enabled, maxInFlight}。
- GET /kernel/plugins/{name}/accounts：只返回公开账号状态、generation、credentialConfigured、额度摘要。
- POST /kernel/plugins/{name}/accounts/{uid}/rotate：{credential, expectedGeneration}，采用完整替换秘密对象；不偷偷保留调用方要删除的旧秘密字段。
- PATCH /kernel/plugins/{name}/accounts/{uid}：enabled/maxInFlight，仅更新公开管理属性。
- 旧 {id, apiKey} 请求通过兼容适配器转换；旧 refresh handler 产生的补丁由适配层显式合并，再提交完整 replacement。

用户轮换与自动刷新都使用 generation 比较并交换；冲突返回 409，不允许旧刷新结果覆盖新凭证。账号 ID 校验防止目录越界，文件创建防重名竞争。启停必须持久化到 envelope，重载与重启后保持；停用后不再发起新租约，已有租约按既有排空策略结束。

### 4.3 迁移

旧平铺凭证读取为 secret 和已知元数据的投影；首次读取不覆盖原文件，首次成功更新才按原子替换写入新格式。迁移测试使用 apiKey 和 cookie+csrf 两种结构。保留单次迁移备份及回退说明；备份也视为秘密，遵守相同权限。

验收：非 apiKey 的合法凭证能添加、轮换、被插件收到；非法结构不能落盘；并发轮换有且仅有一个 expectedGeneration 成功；停用跨重启生效；任何 GET、监控和动作历史都不出现注入的秘密字符串。

## 5. K03：统一 Actions 与调度接入

### 5.1 统一执行通道

新增 ActionRunner，由 HTTP 手动调用和 Scheduler 共用。处理顺序：鉴权 → 查找实际支持动作 → schema 校验 → 固定插件代际及账号 → 获取受限并发许可 → 请求 RPC → 校验结果 → 原子提交允许的状态变化 → 安全审计。

- scope=plugin 或 account；account 作用域必须给 accountId。
- account 作用域的网络动作和聊天共用跨代际账号并发限制；维护操作可使用不要求账号 READY 的许可，避免 reauth_required 账号无法刷新。DISABLED 账号除显式授权的凭证管理动作外不可执行网络动作。
- 超时、客户端取消和插件崩溃均释放许可；后台执行不因请求返回而失去状态管理。
- mutatesCredentials 动作输出的 credentialUpdate 进入 CredentialStore 的 generation 校验，不允许插件自行写宿主文件。
- 调用端指定幂等键；副作用动作执行状态持久化。同一账号、同一动作、同一键不会重复派发。进程中断后无法确认远端结果的状态标记 unknown，禁止自动重放；不承诺远端 exactly-once。
- 自动重试只允许声明安全重试的读动作；签到、领取等动作不因一般网络错误自动重发。

### 5.2 API 与运行记录

- GET /kernel/plugins/{name}/actions：动作定义与可执行状态。
- POST /kernel/plugins/{name}/actions/{id}/runs：{accountId?, input, idempotencyKey?}，返回 202 + runId。
- GET /kernel/action-runs/{runId}：queued/running/succeeded/failed/cancelled/unknown、公开结果或错误码。
- POST /kernel/action-runs/{runId}/cancel：请求取消，最终状态由执行器确定。

动作 ID 和运行记录都绑定插件名称；禁止把一个插件的动作路由到另一个插件。历史有界，输出经 schema 和秘密策略处理；原始 credentialUpdate 不进入结果查询。

旧 task.execute 通过兼容适配器保留；协议 2 的任务统一转为 ActionRunner 调用。记录 nextRunAt、lastRunAt、lastResult、running；同一任务不重入。热重载明确采用取消旧代任务、发布新代任务的顺序，取消也必须形成终态记录。

验收：不存在动作、输入错误、超时、取消、重复幂等键、重载中执行、插件崩溃与副作用结果未知各有回归；手动和定时触发走同一套许可和错误语义。

## 6. K04：多态额度服务与分单位账本

### 6.1 通用快照

新增 QuotaService，插件 quota.query 返回可校验的快照：

```json
{
  "accountId": "a1",
  "observedAt": 1793440000,
  "expiresAt": 1793440300,
  "dimensions": [
    {"id":"daily-chat","kind":"requests","unit":"request","remaining":"85","limit":"100","resetAt":1793462400},
    {"id":"seat","kind":"seat","status":"active"}
  ]
}
```

支持 tokens、requests、points、seat、batches 的明确类型；未识别扩展数据只能放 opaque 扩展区，不参与通用运算。数量用十进制字符串传输和运算，校验非负、有限与单位一致。points 的不同供应商点数不能仅凭 unit=point 合并。

批次包含 batchId、remaining、expiresAt；消费规则由插件提供。宿主只能从有效批次计算展示总量，不推断真实扣费顺序。seat 以状态表达，不伪造百分比。

快照状态区分 known、unknown、stale、unsupported、error。查询失败保留最近一次成功快照和失效标记，不把未知余额显示为零。秘密凭证不进入快照。

### 6.2 同步与调度

- GET /kernel/plugins/{name}/accounts/{uid}/quota：返回快照、来源与新鲜度。
- POST .../quota/refresh：进入受限执行器更新，重入查询合并；无实现时明确 unsupported。
- 健康巡检可按 TTL 安排刷新，禁止每条聊天请求都同步查询上游。
- 新鲜、可靠声明的 exhausted 维度可阻止新调度；unknown/stale 默认只标示，不以推测余额封锁账号。
- 额度不足事件与普通 429 冷却分开记录。只有可靠 resetAt 或后续成功查询才能解除额度阻断；不把所有平台重置时间写死为一小时。
- 凭证 generation 变化时使旧额度快照失效，查询结果提交时核对 generation，避免旧账号会话的余额覆盖新凭证状态。

### 6.3 账本修正

通用轨保留请求、Token、延迟；结算轨按 plugin + unit + dimension 分组，跨账号是否可汇总由同一额度语义决定。禁止返回没有单位的跨平台 vendor_cost 总和。

账本响应新增 settlements[]，保留单条旧 vendor 字段以兼容历史；旧的全局 vendor_cost 只有在单位、平台、维度同质且明确时才可提供，否则返回 null/不提供并标明 mixed。不得把额度同步快照写成消费记录。

流式和非流式均保留上游 usage.vendor，未上报成本为 unknown，不用 Token 估算后冒充真实扣费。历史账本缺单位的记录标记 unclassified，不参与结算加总。

验收：100 points、2 CNY、另一个插件的 50 points 不能合成 152；过期批次不计入可用值；席位不作数值余额；未知与零余额区分；额度查询失败、代际过期、并发刷新、重启恢复都有测试。

## 7. K05：生命周期与公开 API 收口

新服务必须复用现有宿主鉴权、错误分类、跨代并发和原子持久化。临时状态不能与热配置回滚后的实际插件状态相矛盾。

加载顺序：静态 spec 校验 → 秘密无关 init/能力协商 → 服务注册 → 凭证读取 → 可用路由发布。卸载顺序：阻止新调用 → 取消或排空任务/动作/聊天 → 关闭进程 → 注销服务。坏更新保留 last-good，并公开“请求应用失败”，不能仅返回成功。

错误状态冻结：400 参数/schema；401 宿主鉴权；404 插件/账号/动作不存在；409 generation 冲突；413 超大请求；429 宿主并发；501 unsupported；502 上游协议错误；503 插件不可用；504 执行超时。后台 run 的错误以终态和稳定 error.code 表达。

## 9. 实施风险与控制

- 契约改动先落 fixture，再改两端；版本兼容期不静默把旧字段解释成新能力。
- 凭证迁移先做临时副本测试，真实凭证仅在本地受控迁移，不需要贴入聊天。
- 额度和动作有副作用语义，优先冻结未知状态、超时和幂等行为，再接具体业务。
- 所有阶段保持一份明确的当前交付目录；原工作区源码镜像在每阶段验收后同步，避免再次形成两套不同实现。
- 不将此方案写入 README 的“已实现”清单；实现和验收结束后再更新完成状态。
